# ADR-0005: Runtime configuration editor (admin UI)

## Status

Accepted

## Context

The admin UI's Configuration section (`Usage.tsx`) is currently read-only — it displays 5 fields (upstream URL, auto model routing, sanitize system prompt, model baseline lock, DB retention days) sourced from `/admin/status`, which reads directly off the in-memory `Config` object. `admin.py` exposes only `handle_get` by design (see module docstring: "no runtime control to expose via POST" with one backend). `Config` is a non-frozen dataclass parsed once at startup from CLI flags/env vars. It is injected as a **class attribute** on the handler class — `server.make_handler_class()` sets `Handler.config = config` once (`server.py:24`); every request method reads it via `self.config`, which resolves through normal Python attribute lookup to that shared class binding. Nothing currently reassigns `Handler.config` after startup — it is immutable post-construction today.

`~/.anthrouter/config.env` is written by `install.sh` and sourced by the shell launcher shim before the Python process starts (ADR-0001). Python itself never reads this file — env vars only reach `Config` via `os.environ.get()` defaults at argparse time. So a write to `config.env` alone has no effect on the running process; it only affects the *next* process start.

The user wants: a button in the Configuration section opening a modal that shows all current config var/value pairs, lets the user edit them, and applies changes without a full restart, persisting the edit to `config.env` for future restarts too.

This requires two things that don't exist today: (1) a POST/PATCH admin endpoint — a first exception to the read-only-admin design — and (2) an in-memory config mutation path, since `Config` is currently a create-once, read-only-after-startup object with no reload mechanism.

## Decision

- **Scope of editable fields**: all non-structural `ANTHROUTER_*` fields (routing flags, thresholds, sanitizer mode, retention days, etc.) are in the registry, split into two disjoint terms used consistently below: **live-editable** fields apply immediately in-memory on save, and **file-editable** fields are written to `config.env` but only take effect on the next restart. A field is file-editable — marked "restart required" in the UI — if its value is consumed once before the request-handling loop starts (socket bind, file open, DB connection open) or if the process has already derived long-lived state from it that would silently split across old/new callers if the base value changed mid-run. This covers `host`, `port`, `log_file` path, `db_path` (all consumed once at startup) and `upstream_base_url` / the classifier model flags (consumed by `AnthropicTransport` and the classifier client at construction time — changing them live would leave in-flight sessions talking to a stale target while new ones use the new one). Every other `ANTHROUTER_*` field is live-editable by exclusion from this rule. `ANTHROUTER_ADMIN_TOKEN` itself is excluded from the registry entirely (not shown as an editable row, not returned by `GET /admin/config`): it gates the write endpoint that would be used to change it, so editing it live through that same endpoint is a lockout/privilege-escalation footgun. It is changeable only via `config.env`/flag plus a restart, same as before this ADR. A submitted map containing `ANTHROUTER_ADMIN_TOKEN`, or any key outside the registry at all (e.g. a typo'd field name), is rejected with 400 naming the offending key — unrecognized keys are never silently dropped or written to `config.env`, so a client can't mistake a no-op for a successful change or corrupt the file with a stray line.
- **Self-exec restart, considered and rejected**: writing `config.env` then calling `os.execv()` on the running process was considered as a way to avoid in-memory mutation entirely. Rejected because `SessionState` (routing-tier cache, context observations) is in-process memory with no serialization across an exec boundary — a self-exec would silently drop every session's routing history, degrading mid-conversation tier decisions for every active Claude Code session at the moment of an unrelated config edit.
- **Validation reuse requires a prerequisite refactor**: today `parse_args()`'s cross-field checks call `p.error(...)` directly (e.g. `config.py:392,415,444-445`), which calls `ArgumentParser.error()`, which calls `sys.exit(2)` — invoking that path from a running request handler would kill the server process on a bad payload. This ADR requires extracting those checks into a standalone `validate_config(cfg: Config) -> list[str]` that returns error strings instead of exiting; `parse_args()` calls it and converts any returned errors to a single `p.error()` call (preserving today's startup behavior), and the new endpoint calls it directly and turns a non-empty result into a 400 response. This refactor is a prerequisite of this ADR, not an optional cleanup.
- **Write semantics**: validate-then-persist. On save, the endpoint builds a candidate `Config` from the submitted map layered over the current values, runs `validate_config()` on it, and rejects the whole request with 400 and the returned field-level error list if any check fails — no partial write. `validate_config()` also rejects any value that could not be safely written under the quoting rule below (an unescaped `"`, a trailing unescaped `\`, or an embedded newline), so a value that clears validation always writes to a well-formed `config.env` line — the two representations (in-memory `Config` field and on-disk quoted string) never disagree about what's a valid value. Only after validation passes does it persist to `~/.anthrouter/config.env`. The write is **merge, not overwrite**: if the file exists, it reads it, replaces the value of each submitted key in place (or appends it if absent), and leaves every other line — including `install.sh`'s header comments (`install.sh:248-249`) and any key the UI doesn't know about — untouched. If the file does not exist (e.g. the proxy was launched directly, without `install.sh`), the endpoint creates it containing only the submitted keys — it does not pre-populate keys the process loaded purely from CLI flags or ambient environment variables that were never in the file. Values are written using the same shell-quoting convention `install.sh` already uses for `config.env` (`KEY="value"`, double-quoted), so the file stays parseable by the same `set -a; . config.env; set +a` sourcing step. If the file write fails (disk full, permission denied), the endpoint returns 5xx, does not attempt the in-memory reload, and leaves both the file and the running process at their prior values. If the file write succeeds, the endpoint reloads the in-memory `Config` (see Concurrency). A reload failure after a successful write is not expected — the same values just passed validation — but is not provably impossible; if it occurs, `config.env` holds the new values while the running process keeps the old ones until restart. No rollback is implemented for that case; it is an accepted risk, not a proven-unreachable one, and the observable symptom (UI shows a value that doesn't match behavior) is the same signal an operator would use to notice it. File-editable fields are written to the file (so the next restart picks them up **when the process is next started via the `install.sh` launcher shim, which sources `config.env` before invoking Python**) but the running process keeps its old value and the UI shows a "restart to apply" notice for exactly those keys. This guarantee does not extend to a process started by invoking `python -m anthrouter` directly with the same CLI flags each time (documented as a supported invocation in `CLAUDE.md`): argparse gives CLI flags precedence over env vars, so a flag repeated at every direct invocation silently wins over a `config.env` edit on the next restart, with no error and no way for the UI to detect it. The "restart to apply" notice in the modal names this: it says the change takes effect "on the next restart via the installed launcher" rather than promising it unconditionally. The submitted map must include every registry key — both live-editable and file-editable — regardless of whether a given field's value actually changed; a submission missing any registered key is rejected 400 rather than treated as "keep current," since the modal always round-trips the complete set `GET /admin/config` returned and a short submission indicates a client bug, not an intentional partial edit.
- **Concurrency**: `ProxyRequestHandler` serves keep-alive connections on a `ThreadingMixIn` HTTP server (multiple request threads live concurrently), and `Config` is a **class attribute** (`Handler.config`, set once by `server.make_handler_class()` at `server.py:24`) that every request reads via `self.config`. One dedicated `threading.Lock` guards the entire save operation as a single critical section — file read-merge-write followed by the in-memory reload-and-swap — so two concurrent `POST /admin/config` requests can't interleave their file writes; the second waits for the first to finish before reading the file, so its merge is based on the first save's result rather than a stale copy. The reload itself constructs a brand-new `Config` instance by copying the current `Config` dataclass and overwriting exactly the submitted field values (`dataclasses.replace()` or equivalent) — it does not re-invoke `parse_args()` and does not re-read `os.environ`, so a live-editable field also set as an ambient `ANTHROUTER_*` environment variable is not silently reverted to the env-var value on the next reload; the submitted value wins until the next full process restart. The instance is then reassigned via `Handler.config = new_config` — a single reference swap, not field-by-field mutation of the existing instance. An in-flight request thread that already read `self.config` before the swap keeps using the old instance for the rest of that request; any read after the swap gets the new instance. No request ever observes a half-old/half-new `Config`, because the swap is a single attribute assignment. This relies on CPython's GIL making that assignment atomic; `install.sh` and the packaging in `pyproject.toml` assume a standard CPython interpreter throughout (no PyPy/Jython support is documented or tested anywhere in this repo), so requiring CPython here is consistent with, not an addition to, the project's existing deployment assumptions — not a newly introduced gap. Two admins editing concurrently from separate browser tabs is an accepted last-writer-wins race at the *intent* level (the second save's field values simply take precedence) — anthrouter's admin UI has no concept of multiple distinct admin identities to reconcile against, so no staleness token (e.g. a `config_version` field) is introduced; this is a deliberate scope boundary, not an oversight.
- **Editable-field registry**: a single module-level structure in `config.py` (e.g. `EDITABLE_FIELDS: dict[str, bool]` mapping field name to its `restart_required` flag) is the one authoritative source for which fields are editable and which of those need a restart. `validate_config()`, the new GET and POST endpoints, and the modal's field list all derive from this one registry — adding a new `Config` field means adding one entry here, not touching three separate places that could drift out of sync.
- **New admin endpoints**: two additions to `admin.py`, both deriving their field list from the editable-field registry above. `GET /admin/config` (unauthenticated, like every other existing GET endpoint) returns, for each registry field, its `restart_required` boolean and a value — for a live-editable field, the current in-memory `Config` value; for a file-editable field, the value currently in `config.env` (parsed fresh on each GET request; falls back to the in-memory value if the file doesn't exist, matching the direct-invocation path). Reading file-editable fields from the file rather than memory means a pending, not-yet-applied edit is what the modal shows on reopen — closing the loop with the "restart to apply" badge, since the displayed value and the badge now agree on "pending," and a subsequent save's full-registry POST round-trips that pending value instead of silently reverting it back to the still-running in-memory value. `GET` also returns one extra top-level `admin_token_configured` boolean (whether `--admin-token` is set at all) — server-authoritative, so a newly-registered field shows the correct badge without a UI deploy, and the modal can disable Save without ever seeing the token's value. `ANTHROUTER_ADMIN_TOKEN` itself is never included in this response, matching its exclusion from the editable set. `POST /admin/config` is a deliberate, scoped exception to admin.py's read-only design; it is the only POST endpoint and does not open a general control-plane. It accepts the full config key/value map at once (not per-field PATCH), with the same field set the GET endpoint just returned, since the modal always round-trips the complete config it was given.
- **Quoting**: a submitted value that cannot be safely written under the `config.env` writer's `KEY="value"` quoting (an unescaped `"`, a trailing unescaped `\`, or an embedded newline) is rejected by `validate_config()` with a field-level error — never silently escaped or truncated — so the writer only ever receives values it can quote unambiguously.
- **Auth**: `POST /admin/config` is gated behind an `X-Admin-Token` header, checked against a new `--admin-token` / `ANTHROUTER_ADMIN_TOKEN` config flag. If unset (the default, matching every other admin endpoint's current no-auth posture), the write endpoint is unconditionally disabled and returns 403 — a user must opt in to enabling config writes at all. All existing GET endpoints remain unauthenticated regardless of this flag; the token only gates the new write path.
- **UI**: a "Edit configuration" button in the Configuration section opens a modal (not inline edit, not a drawer) listing every field from `GET /admin/config` with its current value, an editable input, and a "restart required" badge on file-editable fields. Save posts the full map; cancel discards. A failed write (e.g. 403 from missing token) surfaces inline in the modal, not as a silent no-op. On a successful save, the modal keeps displaying the values the user just submitted (not a re-fetch from `GET /admin/config`) until the modal is closed and reopened — this avoids the alternative of a live-editable field's new value and a file-editable field's still-old in-memory value appearing side by side indistinguishably from an unchanged/failed save. Reopening the modal later re-fetches from `GET /admin/config` as normal; a file-editable field shows the value currently in `config.env` (its pending, not-yet-applied value if one was saved) alongside the restart-required badge, until the process actually restarts and the two converge.
- **Token delivery**: the admin UI is a static SPA (`anthrouter/ui/dist`, checked in and served as-is — the server injects no per-session secrets into it), so the running proxy has no channel to hand the browser its own `--admin-token` value, and `GET /admin/config` deliberately never returns it. The modal therefore includes its own token-input field, separate from the config fields: the admin pastes the token they set at startup, the value is held only in React component state (not `localStorage`, not a cookie) so it never persists past a page reload, and it is sent as `X-Admin-Token` on the `POST /admin/config` call the Save button triggers. If `--admin-token` was never set, Save is disabled with an inline note directing the admin to set `ANTHROUTER_ADMIN_TOKEN` in `config.env` and restart — matching the auth bullet's "unset means disabled" behavior rather than letting the user discover it only via a 403 after typing a token that was never going to be checked against anything.

## Consequences

- `Config` stops being a create-once-at-startup object for the fields covered by live reload; any future code that assumed `Config` is immutable for the process lifetime (e.g. caches keyed by a config snapshot) must now tolerate a value changing mid-run. `SessionState`'s existing per-session routing-override mechanism is unaffected — it already anticipates the base config value changing under it. Any future collaborator that reads a live-editable field once at its own construction time (the same pattern `AnthropicTransport` and the classifier client already use for the *file-editable* fields, by design) must instead read that field from `Handler.config` per-request; a reviewer adding a new live-editable field should check whether any constructor captures it once at startup, since that would silently stop tracking a live reload.
- Admin surface gains its first mutating endpoint, and thus its first auth mechanism, both deliberately scoped narrowly (one endpoint, one token, full-map-only). Any future write endpoint should reuse this same token rather than inventing a second auth path.
- Because the default is auth-disabled-means-writes-disabled (not auth-disabled-means-open), a user who installs anthrouter and never sets `--admin-token` gets exactly today's read-only admin behavior — no regression in the default security posture.
- `config.env` becomes a file two writers touch: `install.sh` at install time, and the running proxy at edit time. Uninstall (ADR-0001) is unaffected since it only ever deletes the whole `~/.anthrouter` directory tree, not individual keys within `config.env`.
