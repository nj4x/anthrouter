# ADR-0001: Installer config-mutation policy and chain topology

## Status

Accepted

## Context

The anthrouter installer wires the freshly built proxy into an existing Claude Code setup by mutating live files it does not own: `~/.claude/settings.json`, and — in the chained topology only — `~/.caveman/caveman.yaml` and a shell profile's `CAVE_SSRF_ALLOWLIST` export. This is unlike a typical installer that only writes files under its own prefix — a failed or wrong write can silently break the user's Claude Code, or worse, unhook whatever proxy chain was already running.

The dev machine exercises the hardest case directly: `settings.json.env.ANTHROPIC_BASE_URL` already points at caveman (`http://127.0.0.1:8787/w/claude`), caveman's `caveman.yaml` already routes `providers.anthropic.base_url` to anthproxy (`http://127.0.0.1:8082`), and `~/.zshrc` independently exports both a stale `ANTHROPIC_BASE_URL=http://127.0.0.1:8082` (line 160, governs non-Claude-Code clients) and `CAVE_SSRF_ALLOWLIST="127.0.0.1:8082"` (line 174, caveman's SSRF allowlist). `settings.json.env` also already holds a hand-disabled `xxxANTHROPIC_BASE_URL` key from a prior manual edit, establishing (and consuming) a naming convention the installer must not collide with.

anthrouter's port default was already shipped as `8083` in the scaffold commit (`9eac408`), ahead of this ticket's draft text of `8182`; both are free on this machine.

## Decision

- **Port**: keep the shipped default, `8083`. No change to `Config`.
- **`settings.json`**: two recognized states — absent `ANTHROPIC_BASE_URL` (direct topology: Claude Code → anthrouter), or set to the known caveman URL `http://127.0.0.1:8787/w/claude` (chained topology: Claude Code → caveman → anthrouter → api.anthropic.com, `settings.json` untouched, anthrouter wired into `caveman.yaml` instead). The caveman URL match is intentionally hardcoded to this documented caveman default; no override flag is in scope for this ADR. Any third value is refused: abort, print the current value and the manual edit needed, take over nothing.
- **Caveman slot** (`caveman.yaml.providers.anthropic.base_url`): install writes anthrouter's URL unconditionally. If the key was already present (e.g. pointing at anthproxy's `8082`), back up the existing value and record `caveman_slot: backed_up` in the manifest; uninstall restores that value verbatim. If the key was absent, create it fresh and record `caveman_slot: created`; uninstall deletes the key rather than restoring a value. No chaining anthrouter behind another router (rejected — double classification, no material benefit) and no interactive confirmation gate.
- **`settings.json` backup key**: back up under `ANTHROPIC_BASE_URL_ANTHROUTER_BACKUP`, not the ad hoc `xxx`-prefix convention already occupied by a prior manual edit. A named, installer-owned key is unambiguous to both install and uninstall and leaves unrelated `xxx*` entries alone. This is a deliberate deviation from caveman-kit's file-copy approach (which backs up `settings.json` wholesale to `backup/settings.json.bak` and records that path in `manifest.json`): an in-file key backup keeps the settings file internally consistent and avoids a second file to track. The manifest records the backup key name rather than a backup path for this artifact.
- **Shell-level `ANTHROPIC_BASE_URL`** (e.g. `~/.zshrc:160`): never written. It governs non-Claude-Code clients outside either target topology. The installer prints a one-line warning naming the file, line, and current value, and leaves it alone. The warning scan uses the same `$SHELL`-derived target file as `CAVE_SSRF_ALLOWLIST` and is silently skipped if that file is absent.
- **`CAVE_SSRF_ALLOWLIST`**: edited only in the **chained topology** (caveman is in the routing path). In the direct topology caveman is not involved and the allowlist is not touched; the installer prints an informational note that caveman's allowlist was skipped. In the chained topology: append `,127.0.0.1:8083` to the existing export's value rather than adding a second `export` line (a later line would win outright and silently drop the prior allowlist). If no such export exists, add one inside `# >>> anthrouter >>>` / `# <<< anthrouter <<<` markers. Idempotent: parse the current value and skip if `127.0.0.1:8083` is already present; when skipping, the manifest records `allowlist_install_path: skipped` so uninstall takes no action on this field. The port `8083` is hardcoded to the installer default; custom-port configurations are out of scope for this ADR. The manifest records the install path (`append`, `new_block`, or `skipped`); uninstall uses it to determine reversal: remove the value in-place only (for `append`), or remove the entire block including its markers (for `new_block`), so any hosts the user added after install survive an append-path uninstall. Shell support is limited to bash and zsh; target file is `~/.zshrc` or `~/.bashrc` by `$SHELL`; any other shell causes an explicit error naming the unsupported shell.
- **Ceremony**: adopt the pattern from caveman-kit's `install.sh` (`/Users/roman/projects/caveman-kit/install.sh`) with two documented deviations — `~/.anthrouter/backup/`, `manifest.json` recording each backup path (or backup key name, for the `settings.json` in-file backup), `trap ... ERR` invoking `uninstall.sh` as rollback, a `completed: true` field written only after every mutation succeeds, and a re-run guard that refuses with a message naming `uninstall.sh` as the remedy when a completed manifest is already present. An incomplete manifest (present but `completed: true` absent) is treated the same way: run `uninstall.sh` first (it is idempotent) before a fresh install.
- **Uninstall**: For `settings.json` (direct topology only): reads `ANTHROPIC_BASE_URL_ANTHROUTER_BACKUP` from `settings.json` itself, restores it to `ANTHROPIC_BASE_URL`, and removes the backup key. For `caveman.yaml`: if `caveman_slot: backed_up`, restores the backed-up URL verbatim from the manifest; if `caveman_slot: created`, deletes the key. For the shell-profile allowlist: consults the manifest's `allowlist_install_path` — `append` removes only the value in-place (preserving any entries the user added after install); `new_block` removes the entire block including markers. Every restore consults either the live file (`settings.json`) or the manifest (all other artifacts) on each invocation; no consumed or mutated intermediate state is left behind by a partial run. Manifest fields absent due to a partial install are silently skipped; only mutations that were recorded in the manifest can be reversed.
- **Uninstall failure policy**: uninstall is idempotent and re-runnable. Because every restore consults either the live file or the manifest on each invocation (never intermediate state left by a prior partial run), a failed uninstall mid-restore is fully corrected by re-running `uninstall.sh`. No manual recovery steps are required.
- **Startup ordering**: before forking anthrouter, the installer runs pre-flight validation: it resolves the `settings.json` topology (a third-value abort exits here, leaving no orphaned process) and checks that `ANTHROPIC_BASE_URL_ANTHROUTER_BACKUP` does not exist in `settings.json` without an accompanying manifest (orphaned backup key → abort with a message naming the key and file). Only after pre-flight passes does the installer fork anthrouter and health-check it via `GET /health` (an unconditional route, not gated behind `--enable-ui`; see `anthrouter/server.py`), requiring HTTP 2xx, *before* committing any config write. The health check polls every 500 ms for up to 10 s; failure to respond within that window aborts and rolls back. The manifest records the started process's PID in a `pid` field; rollback kills that PID before restoring any config. Config-first would risk leaving Claude Code pointed at a proxy that isn't running. Long-run process supervision (launchd/systemd) is out of scope for the installer; it runs anthrouter foreground/manual and documents that.

## Consequences

- The installer can safely run on a machine mid-chain (caveman → anthproxy) without an interactive prompt, at the cost of being unconditionally destructive to whatever the caveman slot held before. Uninstall is idempotent and re-runnable (every restore consults either the live file or the manifest on each invocation, never consumed state), so a partial or failed uninstall is corrected by re-running `uninstall.sh`.
- Backup artifacts by topology: the direct topology captures only the `settings.json` in-file key; the chained topology captures the `caveman.yaml` slot (backed-up URL or created flag) and the shell-profile allowlist entry (install path). All artifacts must be written to the manifest before their respective mutations, matching caveman-kit's incremental-manifest-write pattern instead of a single end-of-run snapshot. When `caveman_slot: created`, uninstall unconditionally deletes the key — any edits the user made to that caveman slot after install are silently lost; operators who wish to preserve post-install changes to that slot must copy the value before running `uninstall.sh`.
- The stale shell-level `ANTHROPIC_BASE_URL` and its own allowlist entry remain in place after install, which means a plain non-Claude-Code client (curl, SDK script) keeps talking to anthproxy directly, unaffected by anthrouter's installation. This is intentional, not an oversight.
- Chaining anthrouter behind another router is explicitly out of scope; a user who wants that must configure it by hand.
